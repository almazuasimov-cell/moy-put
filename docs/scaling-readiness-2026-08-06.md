# Готовность «Мой путь» к росту — разбор 06.08.2026

Текущее реальное состояние: **7 записей в базе, ~единицы пользователей** — по сути, ещё нет настоящей нагрузки. Все выводы ниже основаны на конфигурации инфраструктуры и коде, а не на измерениях под реальной нагрузкой (её пока не было). Ниже — что понадобится по мере роста, разбито по порогам, с конкретными действиями.

## Текущая инфраструктура (факты)

| | Значение |
|---|---|
| VPS | **1 vCPU**, ~1GB RAM, 9.8GB диск (6.1GB свободно) |
| Backend | uvicorn, **2 воркера** |
| БД | PostgreSQL, пул соединений — **дефолтный** SQLAlchemy (не настроен явно): 5+10 overflow на воркер = до 30 соединений суммарно из 100 доступных |
| Кэш | **Redis не установлен/не используется** |
| Распознавание речи | faster-whisper "base", CPU, int8-квантизация. Загрузка модели — 2.1с (один раз на воркер), сама транскрипция — CPU-bound, полноценно не бенчмаркалась под нагрузкой |
| Мониторинг | Только `journalctl` — нет Sentry/метрик/алертов |
| Деплой | Полностью вручную: `scp` + `systemctl restart`, без CI/CD, без staging |
| Rate-limiting | Только на `/auth/login`, `/auth/register`, `/referral/apply` (nginx). **На дорогих ИИ-эндпоинтах (`/search`, `/biography/generate`, `/entries/process`, `/stt/transcribe`) — нет вообще**, кроме встроенных лимитов бесплатного тарифа |

## Уже исправлено сегодня (важно для готовности к росту)

- ✅ Транскрипция (`local_transcribe`) и загрузка в S3 блокировали **весь event loop воркера**, а не только один запрос — при двух одновременных записях все остальные запросы на этом воркере зависали. Вынесено в threadpool.
- ✅ `/search` и `/biography/generate` были синхронными с блокирующим `time.sleep()` при retry — переведены на async, retry больше не держит поток пула.
- ✅ Гонка (TOCTOU) в проверке лимитов подписки — теперь атомарный SQL UPDATE.
- ✅ Асинхронный DeepSeek везде, где он используется.

Эти фиксы убирают самые грубые причины деградации при **параллельных** запросах — но не решают вопрос **общей пропускной способности** одного слабого сервера.

## 🔴 Что реально ограничивает рост прямо сейчас

1. **1 vCPU — потолок для CPU-bound транскрипции.** faster-whisper работает на процессоре, не на GPU. Даже вынесенная в threadpool, транскрипция одного файла всё равно занимает ядро целиком на время обработки. С одним ядром параллельно эффективно обрабатывается **едва ли больше одной транскрипции одновременно** — остальные будут вставать в очередь, просто не блокируя при этом остальной API (после сегодняшнего фикса).
2. **Нет rate-limit на ИИ-эндпоинты.** Лимиты бесплатного тарифа (3 записи, 1 биография, 5 поисков) защищают от одного пользователя, но не от одновременной нагрузки от многих легитимных пользователей сразу (например, все открыли приложение утром записать дневник).
3. **Нет мониторинга.** Если сервер начнёт захлёбываться при росте, узнаем об этом только когда пользователи начнут жаловаться — нет метрик, нет алертов.
4. **Пул соединений к БД не настроен явно** — работает на дефолтах, что нормально сейчас, но при росте воркеров/нагрузки это стоит сделать осознанным решением, а не оставлять на волю дефолтов.
5. **Деплой полностью ручной** — при росте команды/частоты изменений это станет узким местом и источником ошибок (уже дважды за сегодня файл роутера случайно попадал не в ту папку при деплое).

## Пороги и что делать на каждом

### До ~1 000 пользователей (следующий реалистичный шаг)
Актуальная нагрузка, скорее всего, останется в рамках возможностей текущего сервера — дневник не соцсеть, пики нагрузки короткие (утро/вечер), не все 1000 будут активны одновременно.

**Сделать:**
- Добавить rate-limit в nginx на `/stt/transcribe`, `/search`, `/biography/generate`, `/entries/process` (по IP, щедрый лимит — не блокировать легитимное использование, но защититься от всплесков).
- Подключить простой мониторинг — минимум Netdata (уже стоит на сервере tappp, можно и сюда) или Sentry для бэкенда, чтобы **видеть**, что происходит, до того как пользователи начнут жаловаться.
- Явно настроить пул соединений SQLAlchemy (`pool_size`, `max_overflow`) вместо дефолтов — минимальная работа, убирает неизвестность.
- Настроить staging/тестовое окружение перед проду — сейчас каждый деплой идёт прямо в прод.

**Не делать:** менять сервер, добавлять очереди — рано, нет измеренной необходимости.

### До ~10 000 пользователей — сделано ✅ (06.08.2026)

- ✅ **Транскрипция вынесена в очередь** (RQ + Redis, `backend/queue_service.py`, `backend/jobs.py`) с фиксированным числом воркер-процессов (по числу vCPU) — пиковая нагрузка сглаживается, а не роняет API. HTTP-контракт с Flutter не менялся.
- ✅ **CI/CD** — GitHub Actions, self-hosted runner прямо на VPS (под отдельным urezanным пользователем `deploy`). Push в master → тесты → автодеплой staging; прод — по кнопке (`workflow_dispatch`).
- Не делали: переход на облачный Whisper API (локальный faster-whisper пока справляется) и Redis-кэширование данных подписки (риск отдать устаревшую квоту не оправдан при текущей нагрузке — один индексированный SELECT по `user_id` и так дёшев).

### До ~100 000 пользователей
Это на порядок больше, чем сегодняшняя архитектура вообще проектировалась выдерживать.

**Сделать:**
- Горизонтальное масштабирование: несколько инстансов backend за балансировщиком, а не 2 воркера на одной машине.
- PgBouncer или read-реплики Postgres, если БД станет узким местом (сейчас рано судить — 9МБ данных).
- Полный вынос транскрипции на внешний API или в отдельный, независимо масштабируемый пул воркеров — самостоятельный CPU-bound Whisper на одной VPS здесь уже точно не вариант.
- CDN для APK и статики.
- Бюджет на DeepSeek/S3/Whisper API — расходы растут линейно с пользователями, стоит закладывать заранее, не постфактум.

## Главный принцип (как и у Таппп)

**Не масштабировать раньше измерения.** Делать то, что нужно для следующего порядка величины пользователей (сейчас — до ~1000), а не пытаться сразу спроектировать под 100 000. Сначала — видимость (мониторинг), потом — инфраструктура под реальные цифры, а не под воображаемые.
